# SQLite 迁移方案

日期：2026-10-24。状态：设计草案；本文件只描述迁移目标与实施验收，尚未改变运行行为。

## 1. 目标与范围

在浏览器 Web Worker 中运行 SQLite WASM。进入对话时，根据保存的表格定义和记忆数据初始化内存数据库；SQL 承担查询、填表期间的多步修改和可表达的数据约束。

本次确定的边界：

- 开启“随对话文件同步记忆镜像”时，每次初始化以聊天文件中的有效记忆快照为准；关闭时使用本地保存的数据。开关保持默认开启。
- 同一记忆空间填表期间只允许当前 Agent 写入；界面、宏、查询 Agent 和向量流程继续读取已提交数据。
- 一次填表任务包含的所有分块共用一个 SQLite 事务；运行失败或取消整体回滚，成功后导出完整快照交给保存流程。SQLite 提交后的保存失败单独提示。
- 填表任务、楼层进度、向量任务、记录向量与日志继续使用现有 IndexedDB 存储。存储引擎按职责分别使用。
- 宏界面与宏表达式入口本次不改；现有宏配置通过适配层执行 SQLite 查询。
- 不引入服务器插件、额外数据库服务、OPFS 持久化或每任务工作副本；SQLite 内存库可从已保存数据重建。
- 保留现有本地记忆快照保存能力，以支持关闭同步的模式；其角色调整为序列化保存与恢复，不再并行承担一套在线查询引擎。

“聊天记录”指 ST 的原始消息；导入 SQLite 的是记忆表格数据。原始消息仍由 ST 保存，填表时按任务范围读取，避免复制整段聊天消息进数据库。

本阶段不承诺删除本地保存开关。后续统一以聊天文件为数据来源时，可以删除对应分支，不影响 SQLite 查询和事务设计。

一致性目标以 ST 插件的实际需要为界：保证一次 SQLite 修改完整、快照结构有效、不会把旧对话数据写入新对话。接受崩溃导致最近一次修改丢失、任务状态与数据不同步、楼层进度偶尔不准确。不实现跨引擎原子提交、持久化提交日志、提交回执、崩溃对账或自动重放 Agent。

## 3. 数据职责与运行边界

```text
聊天文件中的记忆快照 ── 同步开启时的初始化来源 ─┐
本地记忆快照         ── 同步关闭时的初始化来源 ─┤
                                              ▼
                                空间运行会话 / SQLite Worker
                                  ├─ Agent 专用事务连接
                                  ├─ 已提交数据读取连接
                                  └─ 完整快照导出与保存
                                              │
                         顺序保存，允许中断 ──┼─ 聊天文件 / 本地快照
                                              └─ IndexedDB 任务、台账与向量
```

### 3.1 运行会话

一个运行会话绑定 `chatIdentity + spaceId + generation`；generation 在初始化、重建、重新加载来源后变化。任务还带独立 `runId`，所有 Worker 请求携带会话身份。回包只交给原会话；失效会话的结果不得应用到新对话。

SQLite 连接由 Worker 持有，功能层仅使用 Memory 对外端口。数据库库文件、SQL 编译、宿主保存 API 都留在 infrastructure；runtime 负责注入和连接各服务。

单空间写入许可覆盖填表、手动编辑、问答填写、导入、清除、删除和应用预设。填表中这些其他写入口显示占用原因并停止提交。配置更改不能绕过许可修改结构或正在使用的数据来源。

写入许可只负责当前插件实例内同空间的串行写入，持续到本次提交与保存调用结束。首版不实现跨标签页或跨设备写锁、版本竞争检查和合并；多个页面同时编辑同一对话可能由后保存的完整快照覆盖前者，接受这项限制。

### 3.2 保持读操作可用

Agent 使用唯一可写连接，从 BEGIN 持续到最终提交。普通读取使用另一份“最近一次 SQLite 已提交快照”初始化的只读内存库；事务提交后整体替换。这里的已提交只表示 SQLite 事务完成，文件保存状态独立显示。

这份只读库属于空间运行会话，所有填表任务共用；不为每个任务复制或合并数据库。采用两份内存数据的代价是内存和快照重建成本，需要实测。

- 表格浏览、查询 Agent、宏重建、向量输入与自动召回均走已提交读取端口。
- Agent 任务内的查询走任务连接，能看到本轮创建和修改的记录。
- 宏 handler 继续同步返回预计算文本，不在宏展开时等待 Worker。
- Worker 队列中一次 SQL 执行仍会占用该 Worker；事务等待模型响应时没有持续执行 SQL。长查询通过执行预算和中断能力终止，不能仅靠 Promise 超时假装 SQL 已停止。
- 初期两个内存连接可在同一个 Worker；这保证主线程响应，不保证长 SQL 与其他 SQL 同时执行。若实测查询延迟不达标，再按性能证据调整 Worker 分工。

## 4. 初始化与数据来源

### 4.1 来源选择规则

| 情况                                         | 行为                                                                             |
| -------------------------------------------- | -------------------------------------------------------------------------------- |
| 同步开启，文件有合法快照且空间绑定一致       | 始终加载文件，即使本地快照时间较新                                               |
| 同步开启，已绑定的旧对话缺少快照，本地有数据 | 一次性迁移：保留本地，确认来源后写入完整文件快照并请求宿主保存；显示实际保存状态 |
| 同步开启，文件快照损坏、版本未知或绑定不符   | 原样保留文件内容，停止该空间初始化；显示具体原因，不自动改用本地数据             |
| 同步关闭                                     | 加载本地完整记忆快照；不读取文件快照来覆盖本地                                   |
| 全新且已保存的对话，无绑定与记忆数据         | 沿用默认表格预设创建空间；写入完整快照和绑定并请求保存后激活，显示实际保存状态   |
| 临时或未保存对话                             | 保持现有未保存提示，不启动填表和记忆写入                                         |

数据来源由设置决定，不比较更新时间来隐式换源。旧数据缺文件时的一次性迁移是明确的数据来源决策，不能自动拿默认空表覆盖现有本地数据。

开关切换只在无活动任务、无正在执行的保存调用时进行。当前页面有已知未保存修改时明确提示，不能借切换开关静默丢弃。关闭同步前保存当前完整快照到本地；重新开启时若文件与本地内容不同，明确选定来源，随后恢复文件优先规则。

### 4.2 初始化顺序

1. 捕获已保存对话身份、绑定、设置和来源快照。
2. 按绑定规则检测身份与分支，暂不读取本地空间执行克隆；同名文件不能仅凭名字认定同一写入目标。
3. 页面重开时把遗留运行任务标记 interrupted，不恢复临时结果、不自动重跑；即使记忆已经保存但任务状态尚未更新，也接受该显示差异。
4. 选择唯一来源，校验格式、完整性和版本，保留表、字段、记录、证据和修订身份；若需要克隆，再以该已验证来源创建新空间并重映射身份。
5. 启动 Worker，创建内存库；启用外键，注册与现有字段语义对应的校验函数。
6. 在初始化事务中创建全部表与辅助关系表，再导入记录、列表、证据与历史。允许引用环时使用可延迟外键，最终提交前检查全部引用。
7. 校验成功后提交初始化事务，生成已提交读取库和宏快照。
8. 根据来源快照标识检查本地楼层台账是否适用，再对照记录 ID、内容指纹、分组定义及 embedding profile 检查既有向量；不匹配的向量不参与检索。
9. 只有 generation 和对话绑定仍匹配时发布 ready；初始化失败保留错误，不发布半成品。

文件加载后可以更新本地快照缓存，但不得通过旧镜像轮询又把旧本地内容写回文件。初始化导入不生成新修订、不产生填表完成台账，也不为每行触发向量请求。

同步开启时，分支克隆必须以当前分支文件携带的有效快照为输入；禁止直接调用现有按本地 sourceSpaceId 克隆的入口。新空间 ID、记录/引用/证据身份重映射完成后，把新绑定与新空间快照通过同一次目标文件保存请求发布。同步关闭时按本地来源克隆。准备或校验失败不修改原绑定，保存失败按第 7 节提示，不发布半成品空间。

本地楼层台账集合附带其对应的 snapshotId，正常保存时在一个短 IndexedDB 事务里更新台账和该标识。重载旧文件或切换来源发现标识不匹配时，不沿用这份较新的 processed 标记，提示进度可能不准确；不进行回执恢复、历史快照对账或初始化触发的自动全量重跑。跨设备和中途关闭后可能需要用户重新选定填表范围，接受这种差异。

进度继承按操作定义：普通记忆编辑或单条记忆删除不自动抹掉过去已处理范围；清除空间记录、应用预设会清空台账，删除空间会删除其台账；克隆/导入不能直接套用同 ID 的旧本地标记。原消息编辑后的进度漂移不在本次建立完整追踪机制，沿用楼层定位并接受进度误差。

### 4.3 文件格式与完整性

文件继续保存引擎无关的 JSON 数据：空间、表、字段、记录、历史、证据。运行数据库结构可变，不把 SQLite 二进制格式作为聊天文件协议。

仅增加完整快照标识 `snapshotId`，用于本地台账关联；保留现有格式版本、spaceId、updatedAt 等字段。record revisionId 继续表达记忆修订；不增加父快照链、commitId 或填表回执。格式变化时沿用现有版本升级与未知版本保护机制。

同步开启后文件承担完整来源，不能继续通过“镜像包含修订历史”开关裁掉正式历史。本次迁移需要将完整历史随文件保存，历史裁剪设置退出该模式；旧文件已经缺失的历史不自动与本地混合，来源选择时展示差异，导入确实存在的数据。关闭同步时，本地快照同样保存完整历史。

## 5. 表结构与约束

### 5.1 动态表映射

- 每个空间运行库仅包含该空间，禁止跨空间查询。
- 每张记忆表格生成一张真实 SQLite 表；标量字段成为列，表/字段 SQL 标识符使用定义 Key，稳定 ID 保存在内部映射中。
- 生成 SQL 标识符时统一使用双引号转义，值用参数绑定。Key 支持中文和 SQL 关键字；禁止保留内部命名空间，并检查 SQLite 标识符大小写规则造成的冲突。
- 保留记录 ID、修订 ID、创建/更新时间等系统列，用户可读，系统写入；Key 改名保留身份，结构变更在无活动任务时重建并验证全部数据后再切换。
- 多选、多引用、短文本列表使用按字段身份生成的子表，保存 ownerId、position、value；保持原有数组顺序、去重规则和可空语义。主记录额外区分 null 与空数组，导出时逐项还原。
- Agent 获得真实表、列与列表子表的 schema 摘要。SQL 文本入口先面向 Agent，宏表达式编辑入口后续单独设计。
- 显示文本沿用当前显示策略与引用解析。SQL 中查询系统显示文本时必须读取当前关系派生的值，不能退回可能过期的存储 displayText。

### 5.2 约束迁移清单

| 现有语义                      | 实施方式                                                        |
| ----------------------------- | --------------------------------------------------------------- |
| ID、定义 Key 唯一             | 主键与 UNIQUE；动态名称冲突在建表前报告                         |
| 必填标量                      | NOT NULL，加现有字段类型对应的空值规则                          |
| 字符串必填、长度与格式        | CHECK 调用与现有 JS trim、UTF-16 长度、正则语义一致的确定性函数 |
| 整数、小数、布尔              | STRICT 类型加范围/有限值/CHECK；布尔映射为 0/1                  |
| 日期、日期时间                | 文本存储，CHECK 调用现有日历合法性规则；保持现有固定格式        |
| 单选、多选选项                | 选项关系表、外键，必要的集合校验                                |
| 单引用、多引用                | 关系外键，目标仍被引用时禁止单独删除                            |
| 多值去重、顺序、必填非空      | 子表唯一约束和 position；跨行的最终必填校验在提交阶段进行       |
| 来源、字段证据、修订历史      | 系统表加写入上下文，由受控写入口和触发器记录变更                |
| Agent 提案限制与用户确认      | 继续由应用层处理                                                |
| embedding、任务状态、文件保存 | 应用层与对应适配器处理                                          |

不能直接把现有 `value.length` 换成 SQLite `length()`：emoji 等输入的计数可能不同；STRICT 也会接受部分无损类型转换，不能承诺保留 JSON 工具的逐类型拒绝行为。现有工具输入继续校验原始类型，SQL 输入采用文档化后的 SQLite 类型语义。

即时 NOT NULL/CHECK 要在每次工具操作结束时满足；不建立只有 ID 且缺必填字段的占位记录。先生成真实记录 ID，创建时提供有效字段，再增加引用；循环引用需要明确的可延迟外键。使用 NO ACTION 的延迟引用检查与现有“单独删除被引用记录失败”的规则分别定义，不能误用即时 RESTRICT 并期待它延迟。

### 5.3 SQL 执行权限

事务控制、结构变更与系统列维护由宿主负责。查询 Agent 只执行只读 SQL；填表 Agent 可执行受控业务表 DML。禁止 Agent 自行 COMMIT、ROLLBACK、修改 PRAGMA、ATTACH、DDL 或直接改系统历史。

权限通过 SQLite authorizer、语句编译结果与执行端口实施，不用正则判断 SQL 读写性质。授权函数与 WASM 绑定、触发器内部写入许可需在技术验证阶段确认。每次工具调用内部可以包含多条 SQL，但整次调用在一个 SAVEPOINT 中执行。

既有结构化 query_records 保留为参数化 SQL 适配入口，便于逐步迁移现有调用与宏；不得同时保留两套不同语义的筛选执行器。保持原有 contains 大小写处理、列表成员匹配、空值、排序及分页行为，用对照测试确认差异。

## 6. 填表事务

### 6.1 事务粒度

一次 FillTask 从第一批 Agent 运行前 BEGIN，到最后一批校验完成后 COMMIT。分块仍控制输入、Prompt 与进度日志；成功处理分块只更新运行进度，不提前标记楼层已完成。

这是对现有“每块原子提交”的明确变更：后续分块失败，前面所有分块的临时记忆一起回滚。任务耗时仍受现有分块超时及取消机制管理，不能把原来的单块时限误当整任务时限。

```text
获得空间写入许可
  BEGIN
    批 1：多轮工具调用，每次调用一个 SAVEPOINT
    批 2：可读取批 1 新建的角色和关系
    ...
    最终约束检查与修订归档
  COMMIT
  发布已提交快照，调用保存，再更新任务与台账
释放空间写入许可
```

SQLite 事务属于连接。调度器只接受持有当前 runId/generation 的任务请求；其他读取走已提交库，不能插入任务事务。等待网络时不保持任何 IndexedDB 事务。

任务启动时冻结本次输入消息、发送者、清洗规则与 Prompt 配置，保存范围和原文指纹。分块使用同一份输入，提交前重新核对原范围：追加范围之外的新消息不影响任务；编辑、删除、swipe 或楼层移位导致输入变化时，终止并回滚，避免将旧内容的记忆记到新楼层上。这个检查只保护当前任务，不建立消息长期版本追踪。

填表前已经存在的 processed/error 台账保持原样。运行进度独立记录为“暂存处理进度”，不能继续用 processedCount 表示已提交进度；失败或取消只记录本次任务结果，不能清掉旧台账或把已有 processed 改成未处理。

### 6.2 SAVEPOINT 与修订

每次写工具操作前建立 SAVEPOINT。约束失败撤销该次调用，让 Agent 看到错误并修正；不可恢复错误终止任务。若 SQLite 错误已导致整个事务回滚，直接终止，不能假定保存点仍存在。内层 RELEASE 不向用户发布任何正式数据。

新记录直接使用最终 recordId，整个任务和所有引用共用它。每次工具操作可以产生内部变更日志，但最终只对受影响记录归档任务开始前的正式旧状态；同条记录本任务多次修改归并为一个最终修订。新建后又删除且没有最终依赖的记录不输出正式记录或历史，日志仍保留操作过程。

已有证据查找与新证据写入均通过任务连接；取消时新证据一起回滚，避免在 IndexedDB 留下未提交证据。操作人、来源楼层和证据身份由工具上下文提供。

### 6.3 取消与切换对话

- 运行阶段接受取消：中断模型/SQL，ROLLBACK，台账保持任务启动前状态，确认回滚后任务才 interrupted。
- 取消与进入提交阶段经过同一个串行闸门。取消先被接受则禁止提交；提交阶段先取得闸门则关闭取消入口并显示“正在保存”，后续取消不能将任务提前置为 interrupted。
- 提交后的取消不能撤销已经提交的记忆；保存协调继续收尾，用户仍可导航查看其他数据。
- 首阶段切换对话允许导航，但会终止旧对话仍在 Agent 运行阶段的任务并回滚。所有迟到回包因 generation 失效被丢弃。
- 如果已经进入保存阶段，保存调用只能使用捕获的原对话身份。宿主只能操作当前 metadata 时，一旦切换就停止该次文件写入并提示未保存；不能把旧结果写进新对话。
- 刷新/关页可能丢失本次未保存结果；任务重开标记 interrupted，不通过保存日志恢复，也不自动重跑 Agent。

后台跨对话继续填表不属于首阶段承诺。当前宿主接口缺少对非活动文件的可确认保存能力，不能只保留 SQLite 连接就宣称后台任务可以安全完成。

### 6.4 任务状态与写入许可

保留现有 `FillTaskStatus` 的 running/succeeded/failed/interrupted。运行会话内部只区分 Agent 运行和提交保存两个阶段；提交保存期间关闭取消和新写入入口。无需为保存失败、结果未知、对账增加持久化任务状态。

| 阶段                             | 是否占用写入名额 | 可接受的操作                                  |
| -------------------------------- | ---------------- | --------------------------------------------- |
| running：Agent 运行中            | 是               | Agent 工具、取消                              |
| running：提交保存中              | 是               | 校验、SQLite 提交和保存；工具与取消入口已关闭 |
| succeeded / failed / interrupted | 否               | 终态；必须已完成收尾或回滚                    |

提交保存调用结束后释放许可，保存失败也不长期锁住空间。已提交数据继续留在当前内存库，显示保存错误；后续保存直接导出当前完整快照。取消终态只在回滚后发布。向量网络请求独立执行，不占用记忆写入许可。

## 7. 保存流程

### 7.1 保证与接受的差异

SQLite 保证事务内的记录、引用、历史和证据一起提交或回滚。SQLite 与聊天文件、IndexedDB 之间按顺序调用保存，不要求共同成功，也不建立跨引擎事务。

任务 succeeded 表示 Agent 已完成、SQLite 已提交且保存调用未报告失败。宿主只提供防抖保存请求时，单独显示“已请求保存”，不能表述为文件已经落盘。宿主可提供真实结果时显示该结果；不为获得落盘确认新增服务端协议或上线门槛。

保留的数据完整性要求：

- 只从完整提交的 SQLite 数据生成快照，先完成序列化与格式校验，再替换保存内容。
- 修改当前 metadata 中插件自己的键，保留最新聊天正文、绑定及其他插件数据；禁止拿任务开始时的整份聊天内容覆盖文件。
- 写入前检查原对话身份，切换后不向新对话写旧数据。
- 文件格式损坏、版本未知时停止导入并保留原内容，不以空数据覆盖。

聊天文件实际落盘由 ST 负责，插件不承诺修复宿主写文件时的损坏。极端情况下允许本次记忆丢失、任务显示与实际保存不一致；不自动重跑 Agent 来修正这些差异。

### 7.2 一次保存的顺序

1. 串行关闭工具与取消入口，核对对话身份、输入和最终约束，完成修订归档；失败则回滚。
2. SQLite COMMIT，导出完整快照并生成 snapshotId；序列化和格式校验通过后，替换只读库并刷新宏与展示。此时只是内存提交完成。
3. 按来源模式保存：同步开启时，将快照写入原对话 metadata 并调用 ST 保存；关闭时，通过一个短 IndexedDB 事务保存本地完整快照。文件模式的本地缓存可以随后更新，不成为文件的替代来源。
4. 保存调用未报告失败后，用一个短 IndexedDB 事务更新任务和楼层台账，并关联本次 snapshotId。空提案也按正常流程完成任务及楼层标记。
5. 释放写入许可。向量沿用已有任务队列和内容指纹检查，独立调度；失败只影响索引，不回滚记忆。

文件保存、本地缓存及任务进度只在当前实例内按序执行。文件已经保存但步骤 4 失败时记录错误并提示进度未更新，不反向撤销文件，也不建立恢复日志。

### 7.3 保存失败与重开

| 情况                               | 行为                                                                                          |
| ---------------------------------- | --------------------------------------------------------------------------------------------- |
| SQLite 提交前失败或取消            | 回滚整次任务，保留原数据和旧台账                                                              |
| SQLite 提交后快照导出或保存失败    | 内存保留完整结果，提示未保存，不更新本次成功台账；任务 failed 并释放许可                      |
| 保存请求已经发出，实际落盘结果未知 | 显示“已请求保存”，接受关页时丢失最近一次结果的可能                                            |
| 记忆已保存，任务或台账更新失败     | 提示进度保存失败，接受两者暂时不同步                                                          |
| 页面重开                           | 根据开关重新读取文件或本地快照，遗留 running 任务标记 interrupted，不恢复临时结果或重放 Agent |

当前页面保存失败后可再次保存当前完整快照，无需重跑 Agent；后续正常修改也会保存最新完整状态。不把失败快照持久化为候选，不跨刷新自动恢复，不长期锁住空间。若导出失败导致读取库仍旧，修复后从已提交写库重建读取库，不向外发布半份数据。

向量沿用已有内容指纹判断有效性；页面重开加载旧记忆后，不匹配的新向量不参与检索。无需新增 commitId、持久化协调待办或跨引擎对账。

## 8. 迁移步骤与交付门槛

各阶段先在开发配置中验证，最终统一切换在线执行路径。读取先迁移、写入仍走旧 Dexie 的开发阶段，必须在每次旧写入后重建 SQLite，或关闭该实验入口；不能把双引擎数据不一致的中间态交付给用户。旧写入路径与新保存协调器不能同时对同一空间生效。

### 阶段 0：验证实际运行条件

- 验证官方 SQLite WASM 在 ST 和目标 WebView 的 Worker 加载、资源路径、CSP 和构建产物；资源随插件发布，不依赖 CDN。
- 使用 oo1/C API 在自有 Worker 中实现最小消息接口；官方 Worker1/Promiser 已标记 deprecated，不作为新架构基础。
- 验证 authorizer、校验函数、SQL 中断、快照导入导出和两个内存库的可用性。
- 验证宿主保存入口与对话身份检查，覆盖单聊和群聊；明确接口能返回的实际结果，不把请求成功当作落盘确认。
- 测量小/中/大空间初始化耗时、峰值内存、查询耗时、完整文件保存体积；保留迁移前基线，给出首屏及读操作是否可接受的结果。

### 阶段 1：初始化与读取迁移

- 新增 SQLite 基础设施与空间运行会话，通过现有 Memory 入口接入。
- 实现来源选择、格式升级、动态 schema、约束映射和完整 JSON 往返。
- 既有结构化查询和宏改走 SQL，宏界面不变。
- 对照现有查询验证空值、列表、文本匹配、系统显示文本、排序、分页和引用显示。

### 阶段 2：快照保存与短写入

- 先接通手动编辑的一次短事务，验证完整快照保存、错误提示和重开加载。
- 将旧镜像轮询写入通道退出，统一由保存协调器负责记忆快照写入。
- 覆盖来源开关切换、预设应用、导入/导出、克隆、清除记录和删除空间；所有写入口使用同一保存协议。
- 文件模式完整历史规则、旧缺失快照迁移提示与本地缓存职责一起交付。

### 阶段 3：填表事务迁移

- Agent 工具读写任务连接，加入调用级 SAVEPOINT 和宿主控制的事务权限。
- 整任务事务替代逐块正式提交；调整修订归档、证据写入、取消与进度语义。
- 将记忆保存与台账更新改为按序调用，接受崩溃时不同步；保留台账集合的简单快照标识，覆盖空提案。
- 使用运行期提交保存阶段保护取消与新写入，保留现有持久化任务状态；冻结任务输入并核对提交前消息变更。
- 问答填写、初始化填表和自动填表复用空间写入许可；显式用户确认的流程保留原有确认边界。

### 阶段 4：接入向量与清理旧路径

- 任务和向量继续保存在 IndexedDB；向量输入读取已提交快照，沿用现有队列与内容指纹机制。
- 停用记忆 Dexie 在线读取与旧提案提交路径，保留本地快照及旧格式导入能力。
- 更新 `CONTEXT.md`、相关 ADR、镜像与用户文档；记录未来宏 SQL 表达式入口所需契约，本阶段不制作新宏编辑器。
- 旧本地数据先保留，迁移并验证成功后再由后续明确的数据清理变更处理，迁移过程不自动删除唯一旧数据。

## 9. 必须通过的场景

1. 文件快照比本地旧但同步开启：仍加载文件；关闭同步则加载本地。损坏/未知版本文件不会被空数据覆盖。
2. 新建角色后，同任务后续工具和分块可以引用该角色；提交前用户查询和宏继续读取旧版本，提交后看到完整新版本及独立保存状态。
3. 第一批成功、第二批失败或用户取消：全部记忆、证据和历史回滚，未处理楼层不新增成功标记，已有台账保持原样。
4. 单工具约束失败可修正继续；事务已整体回滚的错误会终止任务；延迟外键与必填条件在最终提交前检查。
5. 填表期间浏览与滚动可用，其他写入口报告占用；主线程不执行 SQLite，长 SQL 可以实际停止。
6. 切换 A → B：A 运行阶段任务取消并回滚；保存阶段只写 A，无法针对 A 保存则报告未保存，不读取 B 的 metadata。
7. 保存流程各边界失败或关页后，只加载完整有效快照；允许最近修改丢失和进度不一致，不自动重放 Agent。
8. 文件已保存、台账未写完：保留记忆，提示进度误差，不执行对账修复；空提案正常更新任务与台账。
9. 同一实例的并发写入被串行；多标签页/多设备同写接受后保存覆盖，不承诺冲突合并。
10. null/空数组、数组顺序、emoji 长度、正则、日期、循环引用、被引用记录删除与既有类型规则匹配。
11. 初始化、克隆、导入保留正确 ID 映射；已有向量只按有效指纹继续使用，取消任务不产生向量工作。
12. 备份、文件往返包含历史和证据；来源切换不会隐式合并不同快照；本地模式断网保存可用。
13. 文件回退到旧快照：本地台账集合标识不匹配时提示进度可能不准确，不因初始化自动全量重跑。
14. 取消与提交保存同时到达时只产生一个确定结果；保存失败提示错误并释放许可，当前页面可以再次保存完整状态。
15. 提交闸门前编辑/删除/swipe 输入范围内消息会终止提交；范围之外追加消息不使有效任务失败。闸门之后修改原消息接受进度漂移，不加入长期追踪。
16. 分支文件快照早于本地原空间：克隆内容严格来自分支文件，新绑定与新快照同次保存，引用身份映射完整。

## 10. 实施前需要验证的技术点

这些是实现门槛，不改变本文确定的迁移方向：

- ST/目标 WebView 的实际保存入口、可报告的失败和对话切换时的行为。不能假设存在落盘确认或非活动文件保存能力。
- 动态 Key 与 SQLite 名称规则的兼容性；现有合法名称发生冲突时的迁移提示方式。
- 大空间两份内存库、完整 JSON 导出和全量聊天文件保存的实际成本。
- JS 校验函数、列表关系表与触发器组合后的语义一致性；不得通过减少校验让旧数据“看起来能导入”。
