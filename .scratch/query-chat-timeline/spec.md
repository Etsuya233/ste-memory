# 问答面板：Agent 回复按原始顺序渲染为片段时间线

Status: ready-for-agent

## Problem Statement

在 SillyTavern 插件（st-extension）的「问答」Tab 里，Agent 的真实工作流是「思考 → 输出 → 工具调用 → 拿到结果 → 继续思考 → 输出 → 再调用……」的交错过程。但当前渲染把一次回答里**所有思考合并成一个思考块**、**所有输出合并成一段文本**、工具卡集中排在思考与文本之间——原始顺序被丢掉，用户看不出 Agent 是在哪一步思考、哪一步调用工具。同时回答文本是纯文本渲染（无 Markdown），LLM 输出的结构化内容（标题、列表、代码块、表格）读起来很费劲；折叠态的思考块与工具卡 summary 行有 44px 高（移动端触控标准，桌面插件里偏胖），多步骤聊天流显得臃肿。

## Solution

问答面板的每条 Agent 回复改为按**真实发生顺序**渲染的一条**片段时间线**：思考片段（可折叠）、文本片段（Markdown 渲染）、工具调用卡（参数/结果可展开，出现在调用发生的位置，结果回填到同一张卡）。流式期间「正在生成」的片段保持展开实时可见，已完成的片段自动收起、用户手动展开后不会被收回。折叠态整体压缩得更紧凑（summary 高度与卡片内距下调）。回答文本用 Markdown 渲染，思考内容与工具 JSON 保持纯文本/代码块，视觉上明确区分。

## User Stories

1. 作为用户，我想看到 Agent 的思考、回答、工具调用按真实发生顺序逐个出现在时间线上，以便理解 Agent 的推理路径
2. 作为用户，我想每次思考都显示在它发生的位置（而不是全部合并到顶部一个块里），以便看到「思考 → 调用 → 结果 → 再思考」的节奏
3. 作为用户，我想被工具调用隔开的多段思考各自独立成片段，以便区分不同阶段的推理
4. 作为用户，我想工具调用卡出现在触发它的那段内容之后，以便顺序还原 Agent 的动作
5. 作为用户，我想工具调用结果回填进对应卡片（而非另起一块），以便参数与结果始终在同一张卡里对照
6. 作为用户，我想回答文本以 Markdown 渲染（标题、列表、代码块、表格、粗体、任务列表等），以便直接阅读 LLM 的结构化输出
7. 作为用户，我想思考内容保持纯文本（不渲染 Markdown），以便与正式回答在视觉上明确区分
8. 作为用户，我想工具参数与结果保持等宽 JSON 代码块，以便精确检查调用细节
9. 作为用户，我想折叠态的工具卡与思考块更矮（summary 高度 44px → 28px、卡片内距收窄），以便聊天流更紧凑、一眼看到更多步骤
10. 作为用户，我想流式期间「正在生成」的片段保持展开，以便实时观察推理进度
11. 作为用户，我想已完成的思考片段自动折叠，以便不长期占用阅读空间
12. 作为用户，我想手动展开某个已完成片段后它不会被自动收回，以便我可以从容细读任意片段
13. 作为用户，我想执行中的工具卡展开显示参数、出结果后自动折叠，以便实时看到正在调用什么
14. 作为用户，我想失败（isError）的工具卡在结果区显示错误高亮，以便快速定位问题
15. 作为用户，我想模型不支持思考时界面完全不出现思考片段，以便无噪音
16. 作为用户，我想「复制回答」仍复制纯文本（不带 Markdown 标记），以便粘贴到别处不脏
17. 作为用户，我想多轮回传历史仍只回传回答纯文本，以便提示词上下文与现在完全一致
18. 作为用户，我想错误/中止时已生成的片段保持原状并追加错误提示，以便查看中断前发生了什么
19. 作为用户，我想连续同类型增量（如连续思考增量）合并进同一个片段，以便不会出现碎文本块噪音
20. 作为用户，我想 Markdown 里的表格在窄面板内可横向滚动，以便不撑破布局
21. 作为用户，我想 Markdown 外链在新标签页打开，以便不丢失问答上下文
22. 作为用户，我想回答文本中的原始 HTML 不被执行，以便插件不被注入脚本
23. 作为用户，我想流式高频增量更新不卡顿，以便跟手阅读

## Implementation Decisions

- **范围**：只改 apps/st-extension（问答面板）；apps/web 不改任何代码（web 存在同样的扁平化顺序问题，本轮明确后置，另行评估）。
- **消息数据模型**：assistant 消息的扁平字段（thinking 字符串 / text 字符串 / toolCalls 数组）替换为「**片段序列**」作为唯一事实来源。消息仍是：身份、状态（streaming/done/error）、错误信息、填写模式提交结果、有序片段列表。聚合回答纯文本由文本片段推导（用于多轮回传历史与「复制回答」，行为不变）。
- **片段类型**：三种——思考片段（累积文本）、文本片段（累积文本）、工具调用卡（callId、工具名、参数、结果/错误、执行中标记）。
- **片段构建规则**（纯逻辑，事件应用函数内实现）：
  - `thinking_delta` / `message_delta` 追加到当前同类型片段；若当前不是同类型则开启新片段（类型切换即分段，不依赖轮次边界）。
  - `tool_start` 在时间线当前位置插入一张工具调用卡（独立条目，不改变后续增量的"当前片段"归属）。
  - `tool_result` 按 callId 回填对应卡片的结果/错误标记。
  - 事件流本身无轮次边界事件（协议不变），合并规则全部由类型切换驱动。
- **折叠语义**：流式中仅「当前进料片段」受控展开；已完成片段默认折叠、用户手动展开后不被自动收回（已完成块用不受控 details）；工具卡执行中展开、出结果后折叠（继承 ADR 0009 的既有语义）；进行中的思考片段受控展开、用户在流式期间手动折叠不生效（与现状一致）。
- **Markdown 渲染**：为 st-extension 新增 react-markdown + remark-gfm 依赖，随 esbuild 打进 bundle；只渲染**文本片段**。思考片段保持纯文本，工具参数/结果保持 `<pre>` JSON。DOM 映射约定与 apps/web 的 MarkdownContent 一致（表格横向滚动包装、外链新标签页打开）；容器样式用插件自己的设计 token（--stm-*）新写，不移植 web 的样式。react-markdown 默认转义原始 HTML（自带 XSS 防护）。
- **折叠态压缩**：思考块/工具卡 summary 的 min-height 44px → 28px；卡片内距 6px 10px → 4px 8px；assistant 容器 flex gap 8px → 6px。只动尺寸，不动语义（颜色、图标、文案不变）。
- **协议与服务层不变**：SSE 事件类型（thinking_delta / message_delta / tool_start / tool_result / done / error）、QueryChatService 编排、pi AgentEvent 翻译层都不改。
- **ADR**：ADR 0013（apps/st-extension/docs/adr/0013-query-chat-timeline-rendering.md）已随 spec 发布，记录：时间线数据模型与片段构建规则、Markdown 选型（react-markdown 打包 vs ST 全局 marked 的取舍）、以及「web 暂不对齐」这一偏离既有两处同语义约定的决定。

## Testing Decisions

- **好测试的标准**：只测外部行为、不测实现细节。时间线的正确性（保序、同类型合并、工具卡插入与回填、纯文本推导）全部用「事件序列 → 片段序列」的断言表达，不钻 React 内部。
- **主 seam（纯逻辑状态 seam，与 React 无关）**：事件应用函数所在的 query-chat 状态模块。扩展现有 vitest 单测。先例：query-chat/query-chat-state.test.ts（现有 applyQueryChatEvent 测试）。新增用例覆盖：交错事件保序、相邻同类型合并、多次思考片段各自独立、工具卡插入位置与回填、聚合纯文本推导、流式/完成/错误状态。
- **渲染 seam（问答面板组件）**：react-dom/server renderToString 冒烟测试。先例：ui/agent-connection-manager.test.tsx（无 jsdom 的渲染契约测试）。覆盖：片段 DOM 顺序、思考/文本/工具卡节点与 class、details 折叠开合前提、复制按钮取纯文本、Markdown 冒烟渲染（给一段文本断言产出容器）。
- **CSS**：纯视觉改动，无自动化测试，人工验收。

## Out of Scope

- apps/web 的任何改动（含其相同的扁平化顺序问题，单独评估）
- SSE 协议变更 / 引入轮次边界事件（不做按轮分组）
- 工具参数与结果的 Markdown / 富文本渲染（保持 JSON 代码块）
- 思考片段的 Markdown 渲染
- 问答面板的其它行为（硬闸门确认、多轮推进、历史落库、云同步、备份等）
- 用 ST 全局 marked 渲染、与 ST 本体消息同风格

## Further Notes

- **术语**：本次把保序渲染结构定名为「片段」。它与《预设消息》词条 `_Avoid` 列表里的“片段”属不同概念（一个是渲染结构，一个是预设消息条目），不冲突，不改 CONTEXT.md。
- **性能**：流式下每个增量做一次不可变更新（替换末端片段），片段数量少（每轮几个），与现状的字符串拼接同量级，不引入额外优化。
- **与 ADR 0009 的关系**：ADR 0009 定义的「思考块折叠展示、工具卡参数/结果可展开、执行中展开结束后折叠」语义被本 spec 继承并在时间线语义下细化，不推翻 0009。
- 本 spec 交付时已同步发布 ADR 0013（见 Implementation Decisions）。
