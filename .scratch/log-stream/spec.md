# 日志模块重构与填表行流日志

Status: ready-for-agent

## Problem Statement

当前日志模块过于复杂、实时性不足，且与主库纠缠：

- **查看复杂**：填表日志是一条结构化大记录（运行记录），查看器必须按类型解码、嵌套折叠、JSON 展开，还要维护业务摘要与状态文案；新增日志类型就要写新的解码逻辑。
- **实时性差**：日志虽在每批（消息块的一次 Agent 运行）结束时落库，但入口只在任务终态的历史行，且日志页打开后不刷新——用户体感是"整轮填表跑完才能看"，运行中无法看到进度。
- **存储纠缠**：日志与记忆数据同库，schema 变更牵动主库版本，日志还要考虑删空间级联、同步/备份边界。

## Solution

- 日志页变成单纯的**日志查询**：类型/级别/Key 过滤 + 查询按钮（进入页面自动查一次）+ 结果列表 + 点击原样展示文本；查询侧不解析任何业务结构，未知类型也照常显示。
- 填表日志改为**任务 → 批 → 请求**三级行流，**边跑边写**：任务开始/结束、每批开始/结束、每次 LLM 请求各一行；每批首条请求行携带完整系统提示词与预设消息快照，历史上下文批内不重复记录。运行中手动查询即可看到已完成的行，无需等任务结束。
- 日志存入**独立数据库**：不参与云同步、备份与对话文件镜像，不随记忆空间删除级联，旧版结构化日志不迁移、不再显示。
- 任务 Tab 的**活动任务卡片**与历史任务行提供「日志」入口，直达该任务的日志流。

## User Stories

**查询与浏览**

1. 作为用户，我想在日志页按类型筛选（填表任务 / 填表批 / Agent 请求），以便在多种日志记录间聚焦。
2. 作为用户，我想按级别（信息 / 警告 / 错误）筛选日志，以便快速定位异常。
3. 作为用户，我想按 Key（任务 runId）搜索日志，以便定位某次填表任务的全部记录。
4. 作为用户，我想进入日志页时自动执行一次查询，以便立即看到当前数据。
5. 作为用户，我想点击「查询」按钮刷新结果，以便看到刚写入的新日志。
6. 作为用户，我想看到每条日志的时间、类型、级别与 Key，以便识别来源。
7. 作为用户，我想点击一条日志原样查看其文本内容（填表日志为 Pretty JSON），以便直接阅读，不需要理解嵌套结构。
8. 作为用户，我想手动清空全部日志，以便清理敏感内容。
9. 作为用户，我想日志内容可以是任意文本且展示侧不做解析，以便任何日志类型都能被查询与阅读。

**填表行流内容**

10. 作为用户，我想看到填表任务开始（任务楼层范围、每批大小、开始时间），以便确认任务参数。
11. 作为用户，我想看到每个批次的开始与结束（批号、楼层范围、状态、耗时），以便掌握进度并定位失败批次。
12. 作为用户，我想看到每次 LLM 请求一条日志、包含该轮新增消息，以便复盘模型每一步看到了什么。
13. 作为用户，我想看到模型的思考内容，以便理解它的决策过程。
14. 作为用户，我想看到模型输出文本、停止原因与 token 用量，以便评估模型行为。
15. 作为用户，我想看到工具调用的名称与参数，以便判断 Agent 的操作是否正确。
16. 作为用户，我想看到工具结果（含错误标记）落在下一请求行，以便与对应调用配对。
17. 作为用户，我想每批首条请求携带系统提示词与预设消息快照，且历史上下文不重复记录，以便知道模型当时的完整指令环境、同时日志不随轮次膨胀。
18. 作为用户，我想在任务结束时看到状态（成功 / 失败 / 中断）、错误信息、结束时间与耗时，以便快速了解结果。
19. 作为用户，我想失败轮的请求行与批/任务结束行标为错误级别、中断标为警告级别，以便在列表一眼识别。
20. 作为用户，我想初始化填表也按同样结构记录（无楼层范围），以便复盘初始化过程。
21. 作为用户，我想运行中从活动任务卡片进入日志，以便不必等任务结束。
22. 作为用户，我想从历史任务的「日志」按钮直达该任务日志（按 runId 过滤），以便跑完后复盘。
23. 作为用户，我想工具执行后任务直接结束时未落入请求行的工具结果仍被记录在批结束行，以便日志保持完整。
24. 作为用户，我想任务被取消时能看到已发生的行与中断状态，以便确认中断前发生了什么。

**独立性与保留**

25. 作为用户，我想日志独立于记忆空间，删除空间不清日志，以便保留审计记录。
26. 作为用户，我想日志不参与云同步、备份与对话文件镜像，以便对话原文与提示词不离开本地。
27. 作为用户，我想日志超过上限时自动清理最旧条目，以便本地存储不无限增长。
28. 作为用户，我想旧版结构化日志不再显示、也不自动迁移，以便行为简单可预期（审计数据本地可弃）。

## Implementation Decisions

**术语与文档**

- 统一使用「批（批次）」，不再使用 Chunk（已进词汇表 _Avoid_）；「运行记录」= 一批对应的 Agent 运行日志行集合。
- 决策已记录：ADR 0015（独立日志库 + 不透明文本 + 查询式刷新零解析）、ADR 0016（填表三级行流与批内去重）；ADR 0008 加修订指引（快照原则不变，载体改为行流）。旧 spec 被本 spec 取代。

**独立日志库与仓库**

- 新建独立数据库（与主库分离），行结构 `{ id（自增主键）, type, key, level, text, createdAt }`；`text` 是不透明文本，写入方自行组织。
- 全局 1000 行上限：append 后超限在同一事务删最旧（按 id 升序）。
- 无 `spaceId`：不做空间维度过滤、不做删除空间级联；旧主库的日志表原地不动，不读取、不迁移、不删除。
- 仓库端口：`append`、`recent(limit)`、`byKey(key, limit)`、`clearAll`；类型/级别过滤在查询侧内存完成（对已取回结果过滤），不提供 byType/bySpace。

**日志查询页**

- 类型下拉硬编码三个填表类型（`fill-task` / `fill-run` / `fill-agent`）+ 全部；级别下拉 info/warn/error + 全部；Key 文本输入（子串、大小写不敏感）。
- 主查询维度：Key 非空 → 按 Key；否则最近 1000 行；类型/级别在结果上内存过滤。
- 进入页面自动查一次；此后由「查询」按钮刷新；不引入推送、轮询或订阅。
- 结果列表（时间倒序，展示级别徽标、类型、Key、时间）+ 点击单条展开原样文本（`<pre>`，同一时间只展开一条）；顶部「清空日志」。
- 查询侧零业务解析：不再有类型专属摘要、状态文案解码、结构折叠。

**入口与导航**

- 任务 Tab 活动任务卡片新增「日志」按钮（key = 任务 runId 跳转）；历史任务行「日志」按钮保留；焦点消费机制沿用。

**填表行流（key = 任务 runId；每行为 Pretty JSON 文本）**

- 写入策略：边跑边写；每行独立、写失败只记 warn，不阻断任务（best-effort）。
- 行 schema（类型形状，来自本设计会话定稿）：

```jsonc
// fill-task · 开始
{ "phase": "start", "kind": "floor", "range": { "from": 0, "to": 199 }, "batchSize": 20, "startedAt": "…" }
// 初始化填表（kind: "init"）省略 range
// fill-task · 结束
{ "phase": "end", "status": "succeeded|failed|interrupted", "errorMessage": null, "endedAt": "…", "durationMs": 12400 }

// fill-run（每批）· 开始
{ "phase": "start", "batch": 1, "block": { "from": 0, "to": 19 }, "startedAt": "…" }
// fill-run（每批）· 结束
{ "phase": "end", "batch": 1, "block": { "from": 0, "to": 19 }, "status": "…", "errorMessage": null, "endedAt": "…", "durationMs": 12400 }

// fill-agent（每次 LLM 请求）
{
  "batch": 1,
  "block": { "from": 0, "to": 19 },
  "round": 1,
  "systemPrompt": "……",   // 仅每批首条请求行（批内去重）
  "messages": [ /* 相对上一条新出现的内容，pi 原始消息对象 */ ],
  "output": {
    "thinking": "…", "text": "…",
    "stopReason": "toolUse",
    "usage": { "input": 1234, "output": 567, "totalTokens": 1801 },
    "toolCalls": [ { "id": "call_1", "name": "mutate", "args": {} } ]
  }
}
```

- 消息去重：每批首条请求行 = 预设消息 + 本批消息；后续请求行 = 上一轮工具结果。工具结果落在下一请求行；若运行结束时仍有未落行消息（工具执行后直接结束），进所在批结束行的 `trailingMessages`。
- 级别映射：开始行 info；`fill-run` / `fill-task` 结束行按 succeeded/failed/interrupted = info/error/warn；失败轮的请求行 error，其余 info。
- 填表 LLM 端口开启 `includeReasoning` 以捕获思考（模型不支持时静默降级）。

## Testing Decisions

- 好测试的标准：只断言外部行为——"跑完任务后日志库里有什么行、查询时看到什么"，不测捕获内部实现（如何包装流、如何配对事件）。
- 复用现有三层 seam，不新增：
  1. **仓库层**：独立库的日志仓库实现，fake-indexeddb + 测试数据库；断言 append/recent/byKey/clearAll、超限修剪、行结构（无 spaceId）、旧主库表不受影响。先例：`db/log-repository.test.ts`（重写）、`db/fill-task-repository.test.ts`。
  2. **集成层（最高 seam）**：`FillTaskService` 集成测试，沿用脚本化 LLM harness（`scriptedStreamFn` / `gatedStreamFn`）；断言三类行的顺序与内容：任务/批起止、批内去重（首条含 systemPrompt、后续无重复历史）、工具结果落下一请求行、trailingMessages、失败与中断路径的级别与状态。先例：现有 `fill-tasks/fill-task-service.test.ts`（扩展）。
  3. **模型层**：`log-panel-model` 纯逻辑，断言过滤组合（类型/级别/Key 子串）、查询维度选择（Key vs recent）、列表视图模型。先例：`ui/log-panel-model.test.ts`（扩展）。
- 渲染层不测（沿用先例：`tasks-tab.tsx` 无渲染测试）。
- 连带调整：`memory-space-repository` 测试删除"删空间级联删日志"断言；`space-maintenance-service` 的"日志保留"断言改到独立库仓库（或移除）。

## Out of Scope

- 推送 / 轮询 / 订阅式实时刷新与逐字流式直播（查询按需拉取即可）。
- 结构化字段查询、全文检索、按日志内容搜索。
- 日志导出、备份、云同步。
- 旧结构化日志的迁移或兼容展示。
- 其他日志类型（云同步、空间维护等）接入；类型下拉仅填表三类。
- 渲染层组件测试。
