# 问答面板（查询/填写双模式）

插件新增面板 Tab「问答」：与 Agent 聊天的入口，内置「查询 / 填写」两种模式——查询模式由查询 Agent（core QueryAgent）依据记忆空间内容只读回答；填写模式由表格填写 Agent 依据用户指令提出记忆记录变更，经 prompt 软闸门（Agent 陈述变更并征得用户明确同意）后提交落库。定位为用户功能与调试工具兼得：直接问记忆 + 工具调用/思考过程可视化供提示词迭代。

关键取舍：

- **软闸门而非硬闸门**：与 api/web 交互式填写同语义（root ADR 0019 精神），不实现 run 暂停/恢复 + pending 待决状态；误提交由修订历史兜底。硬闸门列为独立后续。
- **零剧情注入**：查询与填写模式都不附对话内容——"把刚才的对话记下来"的场景由后台填表任务（手动楼层范围）承担，交互式填写定位为"用户自描述变更"的精准操作，避免双模式边界模糊与多轮历史膨胀。
- **聊天历史是会话数据不是记忆数据**：按（空间 × 模式）存页面内存，刷新即失；不落 Dexie（不牵动云同步、备份与空间生命周期）、不进通用日志（用户全程在场，无后台复盘场景——与填表日志 ADR 0008 的动机相对）。
- **提示词固定**：查询/填写用 core 固定 composer（`composeQueryAgentSystemPrompt` / `composeInteractiveProposalAgentSystemPrompt`），Agent 提示词预设（ADR 0006）保持填表任务专用。
- **思考流按消费者开关**：LLM 适配器 `includeReasoning` 选项缺省 false（解除 v1「include_reasoning 固定 false」的已知取舍），问答面板开启、填表任务保持 false——已交付行为零变化；思考块经 pi 原生 thinking 事件折叠展示，模型不支持时静默降级。

不选方案：硬闸门确认（api/web 列为非目标，成本高一个量级）；填写模式注入剧情/楼层上下文（与后台填表任务职责重叠）；聊天历史落 Dexie（空间生命周期联动负担，低频价值）；预设档案扩展到查询/填写（v1 成本收益倒挂）；问答运行进通用日志（无后台不可见场景）；「发送到对话」（碰 ST 消息写入契约，风险不值得）。
