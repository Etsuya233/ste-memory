# ADR 0014 — 清洗规则标签模式：不需要正则的清洗路径

## Status

Accepted（grilling 决策确认：Q1 保留=提取中间内容 / Q2 严格区分大小写 / Q3 仅 st-extension、apps 写死正则 / Q4 trim 首尾空白；R1 类型判别数据模型 / R2 新建默认标签 / R3 词汇与 ADR）

## Context

清洗规则（ADR 0011）目前只有正则在一种形态：`pattern` + `flags`，配合保留/去掉/替换。规则面向的普通 ST 用户不会写正则，连「去掉【】里的 OOC」都要查语法，清洗规则列表对新手基本不可用。ST 的 Regex 扩展只有 `findRegex`/`replaceString` 字段，没有 pre/post 标签概念，无法复用来降门槛。同时 apps（api/web）与 st-extension 的清洗规则已经分叉（ST 三模式、apps 只有保留/去掉），apps 后续可能 sunset 或被直接重构进 ST 插件。

## Decision

1. **类型判别**：规则增加 `type: "regex" | "tag"`；`name`/`mode`/`enabled`/`replacement` 两类共享；regex 规则保留 `pattern`+`flags`，tag 规则改用 `pre`+`post`（开始/结束标签）。旧持久化规则没有 `type` → 合并时默认 `"regex"`，无需迁移。
2. **标签语义**：匹配单元 = pre 标签 + 中间内容 + post 标签的整段；「保留」只输出中间内容（剥掉标签），「去掉」删除整段，「替换」把整段换成纯文本替换串。
3. **匹配行为**：pre/post 字面匹配（自动转义正则元字符）、非贪婪（`[\s\S]*?`）跨行、全局（内部强制 `g`）、严格区分大小写；pre/post 保存前 trim 首尾空白；允许 pre===post（如 `**`）；两者都必须非空。
4. **实现**：把 pre/post 编译为 `(?:pre)(inner)(?:post)`，inner 作捕获组 1 → 复用现有 `applyCleaningRule` 的 keep（取捕获组 1）/discard（删匹配）/replace（换匹配）逻辑，变换代码零改动，只换正则来源。
5. **范围**：仅 st-extension；apps（api/web）保持正则不动（不引入 `type`）；core 的「清洗规则」词汇从「正则规则」放宽为「正则或标签规则」。
6. **UI**：规则编辑区加类型选择器，切换只换 `pattern`+`flags` ↔ `pre`+`post` 两块，其余字段共享；新建规则默认标签类型；清洗测试弹窗走同一条流水线照常参与；ST Regex 导入仍只产生正则规则，标签规则只能手动创建。

## Rationale

### 为什么保留 = 提取中间内容（剥标签）

需求字面是「标签及其之间的内容进行保留」，但：新手说「保留【】之间的内容」想的是内容而不是括号；ST 正则最主流的清洗套路就是 `$1` 提取（如 `(\*\*|__)(.*?)\1 → $2`），剥标签后喂给 LLM 更干净；想保留标记语义的用户可以用替换模式把整段换成「标记 + 内容」的形式。该语义一经用户创建 tag 规则就难回退（行为变化会破坏已存规则），故记录为本 ADR。

### 为什么字面匹配 + 严格区分大小写

字面匹配把「会正则」从入门条件里拿掉，是降门槛的核心；进阶用户继续用正则类型。区分大小写对齐 ST 正则默认行为（用户明确选择），且不给 tag 规则引入 flags 心智负担。

### 为什么只做 st-extension

apps 与 st 的清洗规则模型已经分叉（ST 三模式、apps 两模式），apps 后续可能 sunset 或被直接重构进 ST 插件，三套 transform 同步维护成本高收益低。core 共享词汇一并放宽，避免领域定义与实际能力不符。

### 为什么 trim 与允许相同标签

误打首尾空格是新手匹配失败的最大隐形坑，保存前 trim 消除之；pre===post（`**`、`|`）由非贪婪搜索天然支持，无需特判。

## Consequences

- 持久化设置形状新增可选 `type`/`pre`/`post`；旧设置无迁移，合并时按 regex 读入。
- 新建规则默认标签类型，正则用户经类型选择器切换。
- 「保留 = 提取中间内容」成为 tag 规则的固定语义，对 ST 用户可见，未来不得静默改变。
- ST Regex 导入行为不变（仍产生正则规则）；标签规则只能手动创建，不参与导入。
